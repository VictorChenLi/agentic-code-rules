# /next-phase — Execute the Next Phase of a Plan

Read the plan file(s) and any key documents linked below first, then execute the next incomplete phase.

## On completion

- Mark the phase as completed in the plan file's checklist (`[ ]` → `[x]`), and add a checkmark emoji (✅) next to it.
- This repo maintains `context/LOGIC.md` (the architecture/decision log). If the phase changed how something works, update `context/LOGIC.md` to match.

## Self-verification (do this before reporting back)

After implementing the phase, verify as much as possible yourself before surfacing anything to the human.

### Command-line checks (always run these)

1. If the phase touches a TypeScript project, run its typecheck and confirm zero new type errors (pre-existing warnings/errors are acceptable). For a wireframe: `cd wireframes/<project> && npm run typecheck`. For the design system or block library: run `npm run typecheck` in `block-library/` (it also compiles `design-system/` + `blocks/`).
2. Run the linter on every file you edited and confirm zero new lint errors.

### UI checks (run these when the phase has visible UI changes)

> **Always use the Cursor browser tool for UI verification.** Never fall back to `screencapture`, AppleScript, or `osascript` for screenshots unless the user explicitly asks for it.

1. Check whether the relevant dev server is already running (read the terminals folder). If not, start it as a background shell: `cd wireframes/<project> && npm run dev -- --port 5173 --host 127.0.0.1`, then confirm readiness with `curl -sf http://localhost:5173/` (the log prints `127.0.0.1`, not `localhost`).
2. Use the Cursor browser tool to navigate to the running app URL (`http://localhost:5173`, auto-incrementing if the port is taken).
3. Use the Cursor browser tool to take a screenshot of the relevant feature area.
4. If interaction is needed (e.g. clicking a button to open a modal), use the Cursor browser tool's click/interact capability.
5. Verify the key UI changes are present and look correct in the screenshot.
6. If something looks wrong, fix it before reporting back.

## Reporting back

Structure the output as:

### What was done

- Bullet summary of each sub-task implemented.

### Verified by agent

- List each check you ran and what you confirmed (e.g. "TypeScript: 0 new errors", "Screenshot: toggle visible at expected location").
- Embed any screenshots you took inline.

### Still needs human validation

- List only the items you could NOT verify yourself (e.g. correctness that requires comparing numbers, edge cases needing real data, subjective UX judgement).
- Be specific about what to look for and where.

## Key documents

List the plan file(s) and any other key documents that ground this phase before starting work — read them fully first.
